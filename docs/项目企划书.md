## 二、目标用户与痛点

**用户**：在校学生与毕业三年内的职场新人——有收藏习惯、有学习焦虑、时间碎片化。

**痛点**（两层）：
1. 收藏 ≠ 学会：收藏夹是知识坟场，收藏那刻以为会回看，实际再没打开；面对一堆标题不知道哪篇值得花时间；
2. 挑出一篇读，又卡在两处：**不了解的领域**（文章默认的领域共识，新手没有）、**跳跃的逻辑**（作者省略的推导，读者中间掉队）。

**为什么现有方案不够**：原生收藏夹只有列表；通用 AI 问答不接个人收藏、学完不沉淀；学习类 App 的内容不是用户真正想学的那篇。

## 三、产品定义

### 三层能力（★ = 已实现，9/13 交付版）

**第一层 · 看见 ★**
1. 用户用知乎账号登录（OAuth；本地可开本人模式预览，公网部署默认关闭）；
2. 系统读取收藏夹（favlists → favlist_contents 全量分页），带加载反馈与"上次加载时间"；
3. 每条收藏展示：标题 + 三指标**分开展示**（悬停可见计算依据）+ 雷达图 + 收藏时间 + 作者（含认证徽章）+ 正文配图（单图缩略 / 多图并排）；
4. 用户浏览、排序（收藏时间 / 综合分 / 任一单项指标）、分页；
5. 点卡片分流：**已保存全文 → 自动接上上次阅读位置，无记录则从第一段开始**；标题、整卡与按钮保持一致；未保存 → 打开知乎原文，走书签保存（保存完成自动跳回并进入学习）。

**第二层 · 发现 ★（原「替换」演化为「智能推荐」，见变更登记）**
1. 以收藏画像为种子（综合分最高的几篇标题）去知乎搜索同主题公共内容，排除已收藏 / 已保存；
2. 推荐卡片与收藏卡片同构（三指标 + 雷达图），支持「换一批」；
3. 已保存的推荐内容可直接进入学习；未保存的先走书签保存。
> 明确不做「把原收藏替换成别的文章」——收藏是用户自己的选择，产品只做发现与补充。

**第三层 · 学会：逐段精读 ★（取代原「补共识 / 拆逻辑 / 补材料」设想）**
设计定稿见附录 A，实现要点：
1. **AI 分段**：全文切成约 600 字、语义边界优先的段落（模型只给语义分组，字符切点由后端精确计算）；段首尾空白自动清理；
2. **两栏递归模型**：左栏 = 当前层的父文本，右栏 = 它的解释或回答；问原文 → 回答覆盖解释，问解释 → 解释左移成为新的一层；
3. **划选生成个人解释**：任意文本上划选即生成（实线下划线标记、仅本人可见、同账号缓存复用）；解释文本上同样可划选，未改段落的解释树跨版本延续；
4. **私有提问**：打字提问锚定选区或当前层，仅本人可见（虚线标记）；
5. **层级下钻**：点标记逐层深入；同层点击替换、超过 5 层折叠为省略框、只逐层退出；
6. **推进节奏**：底部「我懂了 →」前进、「← 上一段」最小回溯，段控件可展开段列表跳转；
7. **学习记录**：每篇读到第几段自动入库（由埋点派生），侧边栏下拉随时恢复，当前篇高亮；
8. **不替用户读**：解释只补背景与关键断点，推导留给用户自己完成（研究依据见附录 A）。

> 每项列出：候选方案、倾向及理由、状态。由团队逐项确认。

## 一、会话目标

**让用户把收藏的这一篇真正读进去。**

用户收藏了大量回答却没再打开过。会话把这个动作变成一个可完成、有节奏的过程：逐段精读，每段先给一层解释；读不懂的地方自己划出来追问；这段过了，进下一段。

**产品不做什么**：不替用户读、不生成摘要、不做全文总结。产品提供的是**分段 / 解释 / 追问**三层支撑，读的主体始终是用户。

> 更强的目标形态——「会话结束后，用户在没有 AI 辅助的情况下能自己讲出核心论证」——记录为拓展项 E1。

---

## 二、会话结构

### 2.1 分段

会话开始时，AI 把全文划分为若干**适合一次理解**的部分，同时产出一句**全文主旨**（供后续每段解释当上下文）。

划分的硬约束：

| 约束 | 内容 |
|---|---|
| **只定切点，不改文字** | 返回值是字符位置数组，不是重写后的文本。左栏展示的必须是原文本身 |
| **无损** | 各段拼接等于原文，不删减、不改写、不乱序 |
| **有序** | 切点严格递增 |
| **覆盖全文** | 不漏掉任何一段文字 |
| **语义边界优先** | 章节 / 自然段分界优先 |
| **长度上限** | 单段约不超过 1200 字 |

**依据**：Mayer 的**分段原则**（segmenting principle）——复杂内容拆成学习者可控节奏的小段，比连续呈现更利于学习，因为降低了同时处理的认知负荷。

### 2.2 界面

| 位置 | 内容 |
|---|---|
| 左栏 | 当前段的**原文**，可上下滚动，但**限于本段之内** |
| 右栏 | 当前账号在本段的**当前初始解释**（第 2 层），可主动重新生成并保留旧修订 |
| 底部 | 常驻对话栏：输入框 + **提问**（主操作）+ **我懂了** / **上一段**（导航） |

**沉浸优先**：不提供「去知乎看原文」的出口，不做段列表跳转，不显示标注计数。用户留在界面内，一次只看一段。

### 2.3 层级模型

| 层 | 内容 | 可变性 | 可见性 |
|---|---|---|---|
| 1 | 原文（当前段） | 不可改 | 所有人 |
| 2 | 初始解释（每账号每段一个当前修订） | 可主动重新生成 | 当前账号 |
| 3+ | 选区解释 / 提问回答 | 可增可删 | 当前账号 |

第 3 层起以标签页打开，**可嵌套**——在某一层里再次选中，就生出它的子层。

**布局递归**：每一层的结构相同——左边是父文本（含高亮），右边是这一层的解释。用户只看得到自己的父节点，逐级可上溯。整个界面只有一个布局组件。

### 2.4 推进与回溯

**「我懂了」是唯一的推进方式**（滚动限制在段内，跨不过去）。

- 在**第 2 层**按下 → 本段结束，进入下一段
- 在**第 3 层及以下**按下 → 关闭当前层，回到上一层

「我懂了」不改动任何状态，只记一条埋点。

**「上一段」提供最小幅度的回溯**——退回上一段，可连按直到第一段（在第一段时该按钮不可用）。

**只保留这一个按钮，不做段列表、不做跳转。** 理由：破坏沉浸的是菜单和列表，不是后退一步；而「读到第 7 段发现前一段没接上，需要回去看一眼」是必然会出现的理解需求。

**回溯不恢复任何状态。** 退回上一段看到的是本人该段当前解释修订和标记；只是把游标减一。

## 三、两种锚点

| | 选区锚点 | 提问锚点 |
|---|---|---|
| 锚定对象 | 文本区间 | 段落 / 当前层 |
| 占用文字 | **占**，不重叠 | 不占 |
| 可见性 | **仅自己** | **仅自己** |
| 持久性 | 持久 | 持久 |

**节点的可见性由账号归属决定**：初始解释、选区解释和提问整棵树都只对所属账号可见。原文未改且段身份延续时，本人的节点树可跨版本复用；修改或删除的段落在新版不显示旧树。

### 3.1 选区规则

**连续、不重叠、有序、不跨越。**

- 一个选区是一个**连续区间**，不能多段、不能分段选
- 提交前可自由重选或取消（草稿态，松手不等于提交）
- 同一段内两两不相交，按位置有序
- 拖动跨过已有标记时**在边界截断**——已有标记把可选区域切开，跨不过去
- **提交后永久固定，删除才释放**

> 不变式：**一个段落里的所有选区，把该段文字切成若干互不重叠的连续片段。**

### 3.2 统一提问栏

一个按钮管两种情况，靠「有没有输入」判别：

| 选中文本 | 输入内容 | 结果 |
|---|---|---|
| 有 | 无 | **本人选区解释**——占文字区间，仅当前账号可见并按账号缓存 |
| 有 | 有 | **私有提问**——锚定该选区，不占文字 |
| 无 | 有 | **私有提问**——锚定当前段落 / 当前层 |
| 无 | 无 | 按钮禁用 |

**规则：纯选中 = 给自己加一条选区解释；打了字 = 自己的问题。**

这样两种语义自动分开，一个按钮，没有模式切换。提问不注册文字区间，因此不参与「不重叠」规则；选区占用也只在当前账号的树内判断。

## 四、视觉

| 状态 | 视觉 | 生命周期 |
|---|---|---|
| 草稿选区 | 明显的选中高亮 | 临时，提交或取消即消失 |
| 本人选区解释 | **实线**下划线 | 永久 |
| 私有提问锚点 | **虚线**下划线（仅自己可见） | 永久 |

三类用不同的视觉通道，可以叠加——同一段文字既有本人的选区解释、又被自己问过时，实线 + 虚线并存，不打架。

**按下提问钮后标记样式变化，就是提交成功的反馈**，不需要额外提示。

**原则：凡锚在文字上的东西，都在文字上可见。** 不用计数器、不用角标、不用入口文字，右栏保持安静。

## 五、两个出口

| | 我懂了 | 删除解释 |
|---|---|---|
| 关闭窗口 | 是 | 是 |
| 标记 | **不动** | **抹掉**，文字释放 |
| 解释内容 | 保留、缓存命中 | **清除**（含全部子层） |
| 语义 | 收起来 | 不要了 |

**删除仅允许节点所属账号执行。** 删除会释放本人树内对应的选区，不影响其他账号；再次需要时由本人主动重新生成。

**删除的连锁**：标记消失 + 解释清除 + **整棵子树一起走**（子选区长在被删节点的文本里，文本没了就没有依附对象）。兄弟节点不受影响。

## 六、数据与存储

**服务器数据只进数据库**（不使用 SQLite，不使用文件落盘）。

- 数据库负责持久，内存缓存继续负责加速
- 具体选型与表结构待定
- **数据库是部署的前置项**——没连通服务起不来

## 七、状态模型

| 层 | 内容 | 生命周期 |
|---|---|---|
| **全局共享** | 原文版本、段落划分、主旨、版本题库 | 持久 |
| **用户私有** | 初始解释、选区解释、提问及其追问链 | 持久；未改段落跨版本复用 |
| **会话** | 当前段落游标 | 内存 |
| **埋点** | 事件流（open / understood / deleted） | 只追加 |

**埋点与呈现分离**：我懂了只写日志，界面不为它改变任何东西（无已读样式、无个人进度）。

三个可算出的指标：

- **热度** = 某选区被打开次数 → 读者自己标出的难点
- **删除率** = deleted / open → 解释质量，调 prompt 的靶子
- **接受率** = understood / open → 解释有没有效果

**额外收获**：用户的私有提问历史本身就是他的学习记录——在哪几段反复问、问了什么，比任何测验都具体，而且是他自愿留下的。

### B.1 范围与不变式

| 项目 | 固定规则 |
|---|---|
| 付费能力 | `init` 段解释、`explain` 划选解释、`ask` 问答，以及三类的主动重新生成 |
| 免费读取 | 本人已有解释、跨版本复用、历史版本；积分为零仍可读取 |
| 平台成本 | 分段/主旨、配图解释、自测与错题讲解、复习；保留模型用量记录 |
| 周期额度 | 普通用户 50,000 Token/周期；有效高级会员 500,000 Token/周期；先消耗周期额度，超出部分才使用充值钱包 |
| 周期边界 | `Asia/Shanghai` 每日 04:00；周期键取“本地时间减 4 小时后的日期”，操作预留时固化周期，跨 04:00 不迁移 |
| 会员 | 高级会员 19.9 元/月；当前支付关闭，不创建虚假权益 |
| 私有性 | 节点由真实知乎 `uid` 归属；跨版本共享只发生在同一账号 |
| 原文版本 | 每个已发布版本对应不可变 Git commit；正常更新不改写历史 |
| 段落身份 | `segment_id` 是某段文字的一次出现及其可确认的延续，段号只是版内顺序 |
| 生成来源 | 每个节点保存 `generated_commit`，复用不得改写它 |
| 解释树 | 未改段的个人树跨版本持续积累；原文有快照，解释树的后续状态不冻结 |
| 改/删原文段 | 只改变新版段落清单，不删除旧树或账单；旧版仍可查看 |
| 手动删除解释 | 本人软删除该节点及后代，影响本人所有引用版本；删除前提示此影响 |
| 失败计量 | 无可交付结果则不消耗周期 Token、不扣充值积分；已冻结额度全部释放 |
| 积分精度 | `1 积分 = 1,000,000 微积分`；钱包和流水仅存整数微积分 |
| 首版不包含 | 赠送、签到、积分过期、转赠、提现、自动续费、自动充值；不得顺便实现 |

共享功能的成本由平台承担，不代表其中的个人问题、作答或复习内容对其他用户可见。沿用已有内容长度限制、缓存与平台限流。

### B.2 身份、字符坐标与数值

1. 在 `main.py` 统一 `require_account(request)`：会话存在、token 未过期、`profile.uid` 为真实有效知乎标识才成功，返回十进制字符串 uid。所有私人读写、生成、钱包、订单、退款、原文发布均调用它。前端不得指定账务 uid。
2. 修正 `core/oauth.py` 接受 hash_id 却只保存 uid 的不一致。首版缺 uid 返回 `ACCOUNT_ID_REQUIRED`，提示重新授权；禁止用 anon/self/昵称代替真实账号，禁止自动认领旧匿名数据。开发本人模式不得访问真实钱包和支付。
3. 保留知乎 OAuth 和本站 HttpOnly Cookie。私人及账务响应设 `Cache-Control: private, no-store`。注销/换账号清空前端树、版本、预取、钱包和未提交意图；后台已受理操作继续按原账号处理。
4. Git 正文严格 UTF-8。沿用现有导入清洗后的正文作为版本内容；版本存储和比较阶段不增加 trim、换行转换、Unicode 归一化或末尾换行。
5. 后端、数据库、Git 清单的切点、图片位置、选区统一 Unicode 码点，半开区间 `[start,end)`。段内位置相对现有 `_slice()` 去首尾空白后的展示文字。
6. DOM/`KDM.sourceOffset` 保持 UTF-16。API 边界双向转换，拒绝代理对中间下标。新请求传 `offset_encoding:"unicode_codepoint"`。组合字符仍按码点计数；不把视觉上的一个字当作一个位置。
7. JSON 中 bigint ID、Token 计数和微积分使用十进制字符串；有限的段号、长度、位置使用整数 number。Python、SQL 与浏览器不得用浮点数表示额度或钱包。周期 Token 和钱包微积分分别记账，不能把二者合成一个无来源余额。
8. Git object ID 按不透明字符串存储。API 只接受数据库已登记的完整 commit；不得接收任意 revision 表达式、仓库路径或 Git 命令参数。

### B.3 Git 存储与发布顺序

部署采用独立、非公开的内容裸仓库，固定 `CONTENT_GIT_DIR=/data/content.git`。腾讯云 COS 以文件系统方式持久挂载到 `/data`；不使用付费 CFS，应用源码仓库也不存文章历史。镜像安装系统 Git。启动时必须依次验证对象写入/读回和 Git ref 加锁/读取/删除；任一步失败就禁用版本写入，保留数据库当前投影只读，绝不自动退回容器临时目录。个人解释、账户、订单和凭证仍在数据库。Git 历史不能代替独立备份，需共同演练 COS 中的裸仓库与数据库恢复。

每篇文章独立父链；`article_digest=SHA256(article_key的UTF-8)`。每次提交固定三个文件：

```text
content.txt     原文精确字节
meta.json       schema_version=1, article_key, url, title, images, summary, update_id
segments.json   schema_version=1, segments顺序数组
```

清单项：

```json
{"segment_id":"UUID","raw_start":0,"raw_end":120,"text_start":0,"text_end":118,"text_sha256":"hex"}
```

raw 覆盖完整正文；text 是 raw 去首尾空白后的区间。指纹只用于比对，不代替段 ID。JSON 键排序、UTF-8、紧凑分隔符；commit 文件不能写入自身尚未产生的 commit hash。

使用标准 Git `hash-object`、`mktree`、`commit-tree` 创建对象，不共享 checkout/index，不拼 shell。不可变持久引用为 `refs/tags/articles/<article_digest>/<update_id>`，同 ID 不得改指向。`refs/heads/articles/<article_digest>` 可作当前版本投影；唯一业务真源是 `distilled.current_commit`，读取按完整 commit。[Git 对象](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)、[引用旧值校验](https://git-scm.com/docs/git-update-ref)

发布步骤：

1. `begin_content_update` RPC 验证账号、请求指纹、幂等键和 `expected_current_commit`，保存候选内容，不覆盖当前版本。先按uid+幂等键查既有任务并核对指纹，再判断当前基线；成功重放不因latest后来变化而改报冲突。同键同输入重放；不同输入返回 `IDEMPOTENCY_CONFLICT`。
2. 后台领取任务，取得新版主旨及分段，按 B.4 生成清单。任务为 building，已有用户继续读旧版，模型成本归平台。
3. 创建以基线为父提交的候选 commit，写入持久不可变引用。仓库固定core.fsync=all、core.fsyncMethod=fsync，并验证部署Git版本与实际持久卷能力；对象未确认持久化不得发布DB指针。关闭该仓库自动GC，清理/打包另行在已备份维护窗口执行。[Git持久化配置](https://git-scm.com/docs/git-config#Documentation/git-config.txt-corefsync)
4. `publish_content_update` RPC 先重放已published结果，再取得按article_key派生的文章事务锁，覆盖首次尚无distilled行的并发情况；当前指针与基线做NULL安全比较。在一个事务内写版本行、更新当前全文投影/current_commit、标记任务published。两个空基线首次导入只能一个成功。
5. 基线已变则标记 conflict，返回 409 和最新 commit，不覆盖、不自动合并。候选保留，用户查看新版后以新请求重提。
6. DB 提交后才返回成功；可选 Git 文章分支随后用旧值比较更新，失败只修复投影，不回滚已发布版本。

| 故障 | 处理 |
|---|---|
| 分段未完成就退出 | 未派发任务可重领；已派发且结果丢失记平台未知成本，更新终止，用户可新建重试 |
| Git 成功、DB 失败 | 新版不可见，保留引用；同更新 ID 重试发布，不重复生成 |
| DB 成功、响应丢失 | 按更新 ID 返回同一 commit |
| 更新时个人生成未结束 | 结果仍绑定发起时 commit/segment_id，禁止结束时改挂 latest |
| Git 不可用 | 已验证的当前 DB 投影可只读；缺少历史正文缓存返回 `VERSION_STORAGE_UNAVAILABLE`，不得拿新版替代 |
| 恢复旧 DB 备份 | 未在 DB 发布的 Git 候选不自动上线 |

恢复只处理数据库已登记任务。Git创建前先把最终summary/cuts、含UUID的manifest、作者/提交者身份和时间固定在candidate_json；重试不得重造UUID或时间。分段ai_operation_id也持久化，有结果只读原结果。

每次创建Git对象前先检查update_id对应不可变ref；存在则校验父commit、article_key、update_id、正文及manifest指纹，全部相同才恢复candidate_commit和git_saved；不符报GIT_CANDIDATE_CONFLICT，禁止覆盖。ref不存在时以原生“旧ref不存在”条件创建。任务领取/续期/阶段变更均需executor_token匹配；building租期30秒，每10秒续期，只有租期到期且未派发模型或已有持久模型结果才可接管；已派发且无结果等待原操作deadline后终止，不重发。git_saved只重试发布。禁止删除被版本、节点来源、账单引用的commit；首版不做历史压缩/清除业务。

### B.4 跨版本段落对应算法

1. 新旧正文完全相同：保留全部 ID、顺序和切点，包括重复段；标题、图片、主旨可变化。
2. 正文变化：运行 Git diff，固定 `--unified=0 --diff-algorithm=myers --no-indent-heuristic --no-renames --no-color --no-ext-diff --no-textconv --text`，输入为两个正文 blob。解析 hunk，建立未变行区间。仅按 LF 建行号到码点前缀表，正确处理零行插删及无末尾换行，不用默认 splitlines()。
3. 对Git替换hunk内部，再用Python标准库difflib.SequenceMatcher(None,旧hunk码点字符串,新hunk码点字符串,autojunk=False).get_matching_blocks()精化未变区间；只接受正长度块，和相邻Git未变区间仅在两侧坐标连续时合并。旧段完整展示区间落在最终未变区间内时映射到新版，再检查精确相同，形成继承ID候选。这样同一个很长自然段后部修改，不会让其前部未变的精读段因行级diff而失去身份；精化只做原位单调映射，仍接受第5/7条检查，不作为移动或相似语义匹配。[Python difflib](https://docs.python.org/3/library/difflib.html#difflib.SequenceMatcher)
4. 对未映射移动段：其完整展示文字在旧版、新版各出现一次，且新位置两端为完整自然段边界，才继承 ID。旧版因超长保护截在自然段内部的段不使用移动补匹配。
5. 重复文本按整组处理：只有出现次数相同、所有成员均经 Git 单调一对一映射、目标互不重叠，才分别继承。否则歧义组用新 ID；可以保留确定的切点，但不冒认历史解释。
6. 恢复曾删除段：仅处理前述步骤尚未分配身份的区间，不能重复使用本版已分配ID；当前版本继承优先。仅查同文章的已发布祖先；精确文字只对应一个历史段 ID、新版只出现一次且自然段边界完整时恢复该 ID。多候选用新 ID，不选择“最新相似段”。
7. 候选范围互相重叠时取消全部冲突候选的继承，不能按循环顺序挑选。
8. 现有 AI 全文分段返回主旨与建议 cuts；最终只在未保留区间采用建议 cuts 和超长保护。禁止切开或合并保留段。
9. 先按保留段展示起止固定区间，再对剩余文字分段。纯空白间隙并到前一段 raw 尾部，文首空白并入第一段；不生成空展示段。重新计算 raw/text 边界，验证保留段展示文字未变。
10. 发布断言：raw 无缝覆盖 `[0,len(content))`、递增无重叠；text 包含于 raw；本版段 ID 唯一；继承 ID 的文字与历史相同。失败则不发布。

指纹固定：text_sha256=SHA256展示文字的UTF-8字节；manifest_sha256=SHA256最终segments.json字节。匹配仍需实际字符串相等。完整自然段边界指候选起点向前至LF/文首、终点向后至LF/文尾只有_slice会去除的空白，不能匹配更长自然段的子串。重复组按旧精读段展示文字分组；重复判断的出现次数统计该完整展示字符串在各版全部精确出现位置，包含自然段内部，不能只统计已匹配候选。移动/历史恢复另行要求完整自然段边界。内部截断的超长片段只允许Git未变区间及第3条hunk精化产生的原位映射，不参与移动/历史恢复。

V1 `[A,B,C]` → V2 `[A,B修改,D]`：只有 A 复用，B/C 仍可在 V1 看；V3 恢复 C 且满足第 6 条可复用。重复同文段删掉一份后无法确定剩下是哪一份时，宁可不继承，不能串接。[Git diff 官方接口](https://git-scm.com/docs/git-diff)

### B.6 周期额度、积分与充值公式

文字模型固定为 `deepseek-flash`。用户生成只按响应中的 `usage.total_tokens` 计量，固定 `1 Token = 1 积分 = 1,000,000 微积分`；prompt cache命中、未命中、completion和reasoning字段不分别定价，也不能在total之外重复累加。本站已有解释的应用缓存命中不调用模型，消耗为0。

周期键 `quota_period` 的算法固定：把请求时刻转换到 `Asia/Shanghai`，减去4小时后取日期。普通用户额度为50,000 Token/周期，有效高级会员为500,000 Token/周期。高级会员月价19.9元，即1990分；当前支付关闭。每次预留把周期键、会员档位和当期上限写进操作行；同周期内权益升级可把上限从50,000提高到500,000，上限不得因权益随后到期而在本周期内降低。

记 I 为完整消息模板的输入 Token 安全上界，O 为请求的 `max_tokens`，U=I+O。预留与结算固定为：

```text
周期剩余Token = limit_tokens - used_tokens - reserved_tokens
预留周期Token Rd = min(U, 周期剩余Token)
预留钱包微积分 Rw = (U - Rd) × 1,000,000

实际Token T = usage.total_tokens
结算周期Token Dd = min(T, Rd)
结算钱包微积分 Dw = (T - Dd) × 1,000,000
释放周期Token = Rd - Dd
释放钱包微积分 = Rw - Dw

钱包可用微积分 = balance_microcredits
                 - ai_reserved_microcredits
                 - refund_reserved_microcredits
```

预留时在同一事务锁定 `daily_token_quotas(uid,quota_period)`、钱包和操作行，先增加 `reserved_tokens`，只有超额部分才增加钱包 `ai_reserved_microcredits`。结算时必须使用操作行保存的原 `quota_period` 和原预留拆分：即使模型在次日04:00后返回，也不能挪到新周期。成功后 `used_tokens+=Dd,reserved_tokens-=Rd,balance-=Dw,ai_reserved-=Rw`；失败只释放两类冻结。

T 必须是非负整数；若prompt和completion均存在，校验 `total=prompt+completion`。cache hit/miss字段可缺省，存在时只审计；reasoning若为completion子集不另加。缺失total、负数、布尔值、关系不一致、响应模型不在许可集合、T>U或钱包金额溢出，均按 `BILLING_CONTRACT_MISMATCH` 豁免，不用字符数补算，不创建节点。[DeepSeek Token用量](https://api-docs.deepseek.com/zh-cn/quick_start/token_usage/)

报价策略快照只保存 `billing_rule='total_tokens_1_to_1',microcredits_per_token=1000000,requested_model='deepseek-flash',allowed_returned_models,tokenizer_revision,prompt_template_revision,input_token_upper_bound,output_limit`。不保存人民币模型价格、服务费、分时价格或供应商成本。I 必须覆盖实际完整消息模板并由固定版本 tokenizer 或经验证的严格上界得出；quote有效期仍为60秒，排队和执行deadline只服务于恢复，不影响Token单价。

**充值待 JM 最终确认。** 为避免跨任务决定造成数据丢失，暂保留充值钱包、订单和退款设计，但 `RECHARGE_ENABLED=false`。充值兑换率独立命名为 `recharge_credits_per_cny`，不得参与 AI 扣量；未确认前保持NULL且不返回充值档位。若最终保留充值，F为金额“分”、C为订单快照中的正整数兑换率：

```text
充值微积分 = F × C × 10,000
```

C 一旦产生真实充值流水便不能修改历史订单；退款始终按原订单快照换算。会员购买与钱包充值是两个产品，当前都不开放真实支付，不能用充值订单冒充会员权益。

### B.7 报价、生成与解释修订接口

保留现有 `{ok:true,...}` / `{ok:false,error:{code,message,...}}` 包装；新增接口使用正确 HTTP 状态。现有前端 api() 同时检查 HTTP 状态和 ok。RPC所需actor_uid由FastAPI的require_account产生，不能从前端字段透传；service_role JWT只证明后端身份，不能当作终端用户uid。交互式RPC比较actor_uid与目标归属，后台RPC按持久操作归属和executor_token执行。所有付费入口需要真实账号、本站精确 Origin、JSON Content-Type；跨站不能直接调用。

| 接口 | 输入 | 行为/输出 |
|---|---|---|
| `POST /api/reading/open` | url, version可省略, segment_id或start_seg可省略 | 只读已发布版。缺version解析当前；响应返回明确version、manifest及直接目标段；不生成第0段 |

报价协议固定：

1. 用户一次意图使用一个 UUID。网络重试复用它，只有主动再次生成才用新 UUID。同键不同内容409；报价有效期60秒，过期须新报价，不悄悄换价执行。
2. 服务端查验 commit 属于文章、segment_id 是该版成员；parent 必须归本人/同文章/同段，且未删除、位于可生成的当前解释分支。找不到父节点统一 `NODE_NOT_FOUND`，不得退回原文替代。
3. anchor_text 从已授权父文本和码点范围导出；客户端提交的任意 anchor_text 不参与授权或替代真实正文。ask 无范围时使用当前受权父文本/段落和明确问题。
4. messages、`deepseek-flash`模型、输出上限和Token计费策略在quote持久化。预留上限为完整输入Token安全上界加服务端输出上限；若无法建立并验证对应模型预算，禁用新生成，不能把随意倍率称为上限。
5. 前端展示“本周期预计冻结 X Token，超出部分预计冻结 Y 积分；按实际total_tokens结算，多余释放”。手动点击生成/提问/重新生成后执行；自动生成初始解释仅允许在用户已明确开启“进入新段自动生成”且前台确实进入该段时执行。首次默认关闭；该偏好保存在本人的现有会话/前端账号设置，不影响后台预取规则。
6. execute只提交operation_id，不能改目标、messages、计费策略、周期或uid。reserve时重验父节点/替换目标/报价时效、会员权益、原周期开销和钱包余额，缓存命中先于额度判断。
7. 返回202仅表示已受理；前端按operation_id轮询，间隔2秒、离开页面停止轮询但不取消任务。刷新后恢复原操作ID，不能再次创建生成。

重新生成固定为同kind的新节点：replace_node_id必须是本人有效当前分支中的节点；服务端从原节点读取kind、parent_id、范围和question，全部保持原值，客户端同名字段不一致返回REGENERATION_INTENT_MISMATCH。仅根据用户当前选定版本取得标题/主旨等版本上下文。init重新生成必须绕过已有init缓存；选区重叠检查只排除被替换节点本身，其他节点及生成中操作仍需检查。

新节点supersedes_id指向旧节点；finalize在段锁内确认旧节点仍当前，先置其is_current=false，再插入新节点、结算，全部同事务提交。旧内容不覆写，旧追问不迁到新正文。失败则整个事务回退，旧节点仍当前。界面提供“查看上次解释”，历史解释树只读；新追问只挂有效当前分支。

**有效分支判定唯一**：普通列表、缓存命中、选区重叠判断、quote/reserve/finalize，都要求目标节点及沿parent_id到根的每个祖先满足is_current=true且deleted_at IS NULL。旧根被替换后，即使其子节点自己的is_current仍为true，整条分支也不能混入普通列表或接受生成。历史修订读取可忽略is_current，但整条父链仍必须未删除、同uid/article/segment且segment属于所请求版本。新旧修订都保存generated_commit；旧原文版看到的“当前解释”也可能是后来生成的修订，这由B.1的非冻结树语义决定。

删除递归只沿parent_id边，不沿supersedes_id边。删旧修订不删除当前修订；删当前修订不清除以前的修订。删除祖先后不能通过子ID单独读到后代。所有删除均影响本人引用该段的各原文版本，不改变历史扣费。



### B.8 AI 操作、事务与恢复

用户操作状态：`quoted → reserved → dispatched → result_recorded → settled`。缓存命中为独立终态cache_hit，记录result_node_id、冻结/扣费为0，永不派发。其他终止状态：`quote_expired`、`waived_not_dispatched`、`waived_failure`、`waived_unknown`。终态不可重新派发。

所有改变额度或钱包的 RPC 采用同一锁序：有效会员权益 → `daily_token_quotas(uid,quota_period)` → 钱包行 → 用户文章段事务锁 → 操作行 → 节点行。先不加锁读取不可变 uid 和操作预留时刻，再按序加锁。段事务锁使用 PostgreSQL `pg_advisory_xact_lock`，键由明确前缀+uid+article_key+segment_id经固定hash得到；哈希碰撞只造成额外串行，不影响正确性。删除只拿段锁，不反向取得额度或钱包锁。原文发布锁文章行，不更改个人节点。

| RPC | 必须在一个事务内完成 |
|---|---|
| `create_ai_quote(actor_uid,intent,prepared_request,billing_policy)` | 核对幂等和归属，持久化Token上界、固定计费策略及完整服务端输入，各类reserved保持0；缓存命中直接返回cache_hit |
| `reserve_ai_operation(actor_uid,id)` | 验证本人/quoted/未过期/父分支；检查缓存、活跃重复意图和同层选区重叠；计算预留时quota_period与有效会员，先冻结周期Token，超额再冻结钱包微积分，保存拆分和排队deadline，追加一条reserve流水 |
| `mark_ai_dispatched(id,executor_token)` | 只允许reserved被领取一次；持久化执行者token、dispatched、dispatch时间和deadline；提交后才准许调用模型 |
| `record_ai_result(id,executor_token,payload)` | 验证token；dispatched正常记录转result_recorded；result_recorded/settled相同结果重放返回原状态。已waived_unknown的迟到结果只一次性补usage/model/response_id审计，不改终态、额度、节点或流水；不同结果拒绝 |
| `finalize_ai_operation(id)` | 严格读取usage.total_tokens；在原quota_period先结算已冻结周期Token，余量再扣已冻结钱包；重新验证父节点/替换目标仍有效；创建节点/切换当前修订、释放两类剩余冻结、记录settled流水及result_node_id |
| `waive_ai_operation(id,reason)` | 验证可豁免条件；释放预留、写唯一release流水、记终态；已知成本保留，未知NULL |
| `delete_private_node_tree(actor_uid,id)` | 段锁内复核归属，递归只处理同uid/article/segment，软删除整树；不删钱包和用量；正在生成子节点在finalize重新验证时失败且不扣 |

流水 event_key 固定为 `ai:<id>:reserve`、`ai:<id>:settle` 或 `ai:<id>:release`。每行分别保存周期Token与钱包微积分的变化。最终结算和释放互斥，由操作行终态决定，不允许同时出现。所有 RPC 重放返回原结果，不再改变额度或钱包。quoted到期直接quote_expired，无冻结和流水；终态缓存/操作重放不得重新调用模型。

额度变化：预留 `Rd/Rw` 时 `daily.reserved+=Rd,wallet.ai_reserved+=Rw`；成功结算 `Dd/Dw` 时 `daily.used+=Dd,daily.reserved-=Rd,wallet.balance-=Dw,wallet.ai_reserved-=Rw`；失败只释放原 `Rd/Rw`。可用量不单独存储。先查额度或余额、再分开更新多表属于禁止实现。

模型结果持久化时固定result_hash=SHA256规范化JSON的UTF-8字节；JSON由content、response_id、returned_model、created、finish_reason和usage这六项组成，键排序并采用B.3相同编码规则。result_hash创建后不可更改；重放核对该hash，结算后即使清除result_json仍可判重。result_node_id和账单不可因内容删除而清除；操作重放若对应节点已被软删除，只返回result_deleted=true、原状态/收费，不返回正文、不重新生成。

成功前置：非空有效文本、可交付完成状态、有效 `usage.total_tokens`、响应模型为许可的 `deepseek-flash`标识、实际Token不超过预留总上界、父节点与原锚点仍有效。节点和两类额度结算必须在同一finalize事务提交；AI调用层只记录结果，不能直接扣量。生成期间父节点被删除/替换时记 `waived_failure/PARENT_CHANGED`，不复活旧树。

预算异常处理固定：若实际Token超过预留上界，或模型/usage与固定规则不一致，用户两类消耗均为0，释放冻结，记录`BILLING_CONTRACT_MISMATCH`，并关闭billing_settings的新生成。新调用返回`BILLING_CONFIG_UNAVAILABLE`，直到核对模型和预算规则；不追扣用户，不把此分支当成常规低估策略。quote/reserve/mark_dispatched三处检查启用状态；普通BILLING_ENABLED关闭只停止新派发，不影响有效在途结算。豁免和停用以成功事务提交并返回业务错误，不得RAISE导致修改回滚。

**执行与恢复机制**

- 在现有 FastAPI 生命周期内新增有限后台执行循环，保留原store初始化；不引入Redis/Celery或新常驻服务。操作先入DB，工作循环再以数据库原子领取方式处理。单实例沿用当前部署；多个worker也只能有一个领取同一操作。
- `AI_WORKER_CONCURRENCY=4`、领取间隔1秒、恢复扫描间隔30秒。这些是工程初始参数，可调；不作为收费产品参数。后台task持有强引用，关闭时停止领取并等待在途任务到限时。
- reserved最多排队60秒，未派发到期转waived_not_dispatched并释放原周期Token和钱包冻结。dispatched 使用 `asyncio.timeout(180)` 限制整个非流式调用，并保留60秒结果写库窗口，deadline=dispatch+240秒。httpx仍trust_env=False。
- 调用前持久化dispatched；同一个operation最多由取得executor_token的执行者发起一次HTTP请求。没有确认过的供应商幂等或结果重取接口，首版不承诺外部exactly-once，也不自动重发dispatched操作。
- 当前任务可重试记录同一份模型响应到DB，不能重试模型本身。记录成功后即使用户断开，恢复循环继续finalize。
- 恢复扫描先finalize result_recorded，再处理过期reserved/dispatched。领取结果用行锁/状态条件更新，不能内存判断后无条件更新。
- dispatched到deadline仍无持久结果：waived_unknown，两类charged均为0并释放原冻结；迟到结果只补用量审计，不再扣量、不新建结果、不复活操作。
- 已有有效usage但输出为空、截断或无法交付：waived_failure，不消耗用户周期额度或钱包。上游报错不得用估算Token替代真实usage。
- result_recorded后DB结算失败：保持处理中，只重试finalize。没有结算成功不得向前端声称付费结果成功；前端能按operation_id恢复。
- 平台模型功能也写ai_operations的platform记录，用户周期和钱包冻结/扣除恒0。现有共享缓存命中不调用模型，不产生假用量。供应商prompt cache命中仍包含在真实total_tokens中；只有本站结果缓存命中才是用户0消耗。

### B.9 会员、充值、积分入账与退款

首版会员价格固定为高级版 19.9 元/月，但会员购买、自动续费、充值和退款全部关闭；接口只能返回产品说明与不可购买状态，不得创建真实订单。充值设计因产品取舍尚待 JM 最终确认，以下支付、入账和退款协议仅作为保留的条件设计；只有完成商户主体、Native 权限、AppID 绑定和“AI 服务预付积分”准入核验，并由 JM 明确开启后才可启用。浏览器始终只访问现有 FastAPI，后端才可调用 CloudBase 官方 pay-common。[微信 Native 接入](https://pay.wechatpay.cn/doc/v3/merchant/4015614538)

| 本站接口 | 输入及行为 |
|---|---|
| `GET /api/billing/account` | 本人会员档位、原始额度周期、周期Token上限/已用/冻结/可用量，以及钱包积分/冻结；不返回密钥 |
| `GET /api/billing/ledger` | 游标分页，默认20/最多100，倒序；仅本人。区分周期Token与充值钱包微积分，预留行不冒充消费 |
| `GET /api/billing/plans` | 返回高级版 19.9 元/月的展示信息和 `membership_purchase_available=false`；充值待 JM 确认，默认 `recharge_available=false` |
| `POST /api/billing/orders` | 默认返回 `PAYMENT_DISABLED`。未来开启后仅接收服务端已配置 `plan_id` 与 `idempotency_key`，不接收任意金额或积分数 |
| `GET /api/billing/orders` | 本人充值记录，游标分页 |
| `GET /api/billing/orders/{id}` | 仅本人，可触发受限服务端查单；返回pending/paid/closed/failed和二维码状态 |
| `POST /api/billing/refunds` | `{order_id,amount_fen,idempotency_key}`；验证可退条件后原子预留，再调用退款 |
| `GET /api/billing/refunds/{id}` | 本人退款状态与冻结积分 |

未来开启充值时，新订单号用UUID的32位hex；退款号用独立UUID的32位hex。支付订单保存当时商户、AppID、金额、`recharge_credits_per_cny`及对应积分，重试不能重定价。退款原路退回，不实现积分兑换现金。会员订单与充值订单分开建模；支付关闭期间不得创建两者中的任何真实订单。

**支付状态机**：created → pending → paid；未支付分支可为closed/failed。provider_state单独保存。paid不因退款而退回pending。

1. `create_payment_order` RPC 先幂等建本地订单。外部下单在事务外；返回二维码后保存code_url和provider状态。
2. 外部下单超时保持原订单，使用原out_trade_no查单；不能换单号把可能已付款的旧单遗忘。
3. 到账由服务端可信查单结果驱动 `apply_payment_query` RPC，核对merchant_id、app_id、out_trade_no、transaction_id、currency=CNY及amount.total与本地订单完全一致。
4. 同一个事务把订单置paid、`balance += credit_microcredits`、追加 `pay:<order_id>:credit` 唯一流水。transaction_id唯一，不能被另一订单复用。
5. 浏览器跳转、用户截图、前端传回SUCCESS、未经核验通知均不能入账。重复或乱序通知只触发同一订单查询。
6. 二维码展示10分钟后停止等待；先查单再关单。只有微信确认关闭才置closed；关单遇已支付走正常入账。前端定时器不能直接改订单状态。

**官方支付集成的最小改动**

- 正向链路：FastAPI服务端API Key作为Bearer，调用 `POST https://<env>.api.tcloudbasegateway.com/v1/functions/<实际函数名>?webfn=true`。该函数安全规则invoke:false，禁止非管理员调用；不得向浏览器发Key，也不另开绕过网关的公网Express入口。[服务端API Key](https://docs.cloudbase.net/api-reference/webv2/api-key)、[函数调用](https://docs.cloudbase.net/cloud-function/function-calls/)、[安全规则](https://docs.cloudbase.net/cloud-function/security-rules)
- 固定官方action白名单：wxpay_order_native、wxpay_query_order_by_out_trade_no、wxpay_close_order、wxpay_refund、wxpay_refund_query以及支付/退款通知；关闭商家转账等其他业务。
- 订单金额、描述、币种、商户和回调地址由本地订单和部署配置构造。二维码直接编码官方code_url，不经第三方二维码服务。[官方Native集成](https://docs.cloudbase.net/integration/wechat-pay-native)
- 基于官方模板现有 `services/payService.js`、`services/orderService.js` 和controller/middleware改动，不自行实现支付签名。正向调用先依赖官方管理员网关鉴权，再要求标准Bearer值与云函数Secret中专供该后端使用的服务端API Key常量时间比较；缺失/不符403，无环境/header放行fallback。不要覆盖环境其他函数权限。独立支付/退款回调入口不走正向action权限，只能对已登记单号进行可信查单；保留集成中心合法回调入口。
- 支付通知只取out_trade_no作线索，先用已有strategy.query主动查询微信；退款用strategy.queryRefund。取得真实结果后，orderService业务hook用服务端API Key直接调用同一PG到账/退款RPC。
- 将模板未等待的handlerUnifiedTrigger/handlerRefundTrigger后台调用改为await，数据库提交后再返回成功；查单或DB失败返回错误。仍保留周期查单补偿，不依赖通知绝不丢失。
- 不直接信任通知中的ParsedContent/金额/trade_state。伪造通知最多触发受限查一个本地已存在订单，不能创造积分。[官方模板源码](https://raw.githubusercontent.com/TencentCloudBase/awesome-cloudbase-examples/master/integration/cloudbase-wx-pay/functions/pay-common/services/payService.js)

**退款公式与状态**

```text
订单可退分 = 原订单金额 - 已成功退款分 - 非终态已预留退款分
钱包可退分 = floor((balance-ai_reserved-refund_reserved)/(C*10,000))
本次退款F必须满足 0<F<=min(订单可退分,钱包可退分)
冻结微积分Q = F*C*10,000
```

首版无赠送，积分可混用，因此不增加逐充值批次消耗分摊表。不足一分钱对应的积分留在钱包。还需满足上线时已核验的渠道退款期限/次数限制；不把钱包公式当成全部渠道条件。[微信退款实践](https://pay.wechatpay.cn/doc/v3/merchant/4014959631)

`reserve_refund` 按钱包→订单→退款锁序，原子校验并增加refund_reserved，写 `refund:<id>:reserve`。外部请求用同一out_refund_no和固定金额。状态：reserved → submitted/processing → succeeded；发送结果不明为submission_unknown；ABNORMAL为review_required，继续冻结；只有确知未退款且已终止/CLOSED才失败释放。

`apply_refund_query`核对out_refund_no/out_trade_no/transaction_id/refund_id/amount.total/amount.refund/amount.currency；退款响应不保证包含mchid/appid，商户校验取本地订单快照与本次受认证SDK固定商户上下文一致，不能索取不存在的响应字段；SUCCESS时 `balance-=Q, refund_reserved-=Q`，追加 `refund:<id>:settle`；明确失败释放仅 `refund_reserved-=Q`，追加release。超时、429、500不能释放；succeeded不得被迟到通知降级。已CLOSED之后重新申请属于新退款，重新检查余额。

**补偿与对账**

复用B.8的恢复循环。扫描用FOR UPDATE SKIP LOCKED领取到期行，写executor_token及30秒lease；网络调用超时20秒，状态落库校验token，过期执行者不能更新扫描状态。支付首次5秒，随后30秒/120秒/600秒；退款首次60秒，随后120秒/600秒，不明确持续600秒核对。

created支付单恢复先查单：确认不存在且本地未过期，用原单号/原参数补首次下单；过期且确认未创建才关闭本地单。reserved/submission_unknown退款先查单，RESOURCE_NOT_EXISTS后按原退款号/原参数重提，不直接释放。其他查询错误保持未决。日常退款必须先在本站建本地退款单，商户控制台仅处理已关联本地单的异常，不能绕过冻结。支付闭合状态停止扫描，已支付单上的退款继续独立扫描。每日对仍异常记录生成运营查询结果，不向用户伪报成功。页面打开与否不影响入账；回调全丢也能通过查单入账。支持用同一服务端检查入口按指定订单强制核对，不直接手改余额。



### B.10 导入、历史记录与共享功能

**新导入协议**

| 接口 | 固定契约 |
|---|---|
| `POST /api/ingest`，preview_only=true | 同源已登录；接收url/title/content/images/offset_encoding，按既有约束清洗、精确校验hostname，返回当前commit和新旧内容是否相同；不调用AI、不发布 |
| `POST /api/ingest`，preview_only=false | 增加idempotency_key和expected_current_commit（首次为null），返回202及update_id；候选输入指纹绑定全部清洗后内容与基线 |

同一正文、标题和规范化图片数组均与当前一致时，最终提交直接返回当前版本及unchanged=true，不调AI、不造新commit。只有图片变化时保留既有summary/cuts/段ID；标题或正文变化时重算主旨，段落继承仍按B.4。

所有导入限长沿用服务端现有常量。使用URL解析得到hostname，对本站支持的知乎文章/回答域名与路径做明确白名单，禁止 `"zhihu.com" in url`。保留现有回答URL归一化规则。预览期间当前版本改变，最终提交409，不静默发布到另一基线。

**书签升级使用浏览器标准通信**

现有书签跨站fetch不带本站Cookie，SameSite=Lax也不支持用简单credentials:include解决。复用已有首页的 `?import=1` 模式：

1. 用户点击书签时同步 `window.open(本站/?import=1)`，保留popup句柄；被拦截则当场提示。正文不放URL，身份令牌不传到知乎页面。
2. 本站弹窗向允许的知乎origin发送READY；书签仅接受event.source===popup且event.origin===本站origin的READY，再用精确targetOrigin发送结构化IMPORT消息。
3. 弹窗仅接受event.source===window.opener，origin精确属于当前支持的 `https://www.zhihu.com` 或 `https://zhuanlan.zhihu.com`，消息type/字段/长度合法。不得用星号targetOrigin发送正文。
4. 正文暂存在本站该tab的sessionStorage。未登录走现有OAuth的next回到 `/?import=1`；回来后同源预览并提交。完成/取消删除临时正文；无法保留opener或登录返回状态时明确提示重新点击书签，不悄悄丢数据。
5. 新版导入页面显示当前版本及“保存为新版本”，确认后才提交；首版直接确认保存。成功跳到带明确version的阅读URL，不自动生成未授权的付费解释。
6. 保留旧 `/api/ingest` 对上述精确知乎origin的无凭据预检/错误响应，仅返回 `BOOKMARKLET_UPDATE_REQUIRED` 和升级说明；不允许匿名写入。不要为了兼容旧书签继续接受匿名发布。

这些使用现有Cookie、OAuth和postMessage，不另造长期导入token。[MDN Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)、[MDN postMessage](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage)

**版本关联的其他功能**

- 分段与主旨使用请求commit的固定清单。配图解释按article+commit+URL缓存；图片位置从该版原文计算。
- 自测题库按article+commit持久化，冲突时读取已存在的胜出题库，不把未保存的另一套题返回用户。提交答案必须带commit和quiz_hash，hash不匹配返回QUIZ_VERSION_MISMATCH；不得按latest判旧题答案。
- 复习保持现有输入与呈现方式。general有个人问答输入时，缓存键为uid+article+commit+实际输入指纹；无个人输入可按article+commit+输入指纹共享。personal继续不共享，费用都由平台承担。不要顺便把现有list_user_questions返回的回答content改为question而改变模型口径。
- 原文新版本不删除旧题库/作答；旧作答不成为新版复习的依据。只有当前所选版本的段成员对应的个人节点可进入该版复习上下文。
- 学习历史同一文章显示一条最近阅读记录，记录内带commit、segment_id；按事件时间及事件ID确定最近项。恢复先打开该commit和目标段，不能先生成0段，再跳历史段。

### B.12 旧数据迁移与回退

迁移在短维护窗口内进行：暂停导入、生成、删除和作答写入；原文可只读。先迁移会员权益、各账号当前周期额度与空钱包，再开放Token计量；支付和充值仍保持关闭。不得一边允许旧匿名/共享写入，一边切私有读取。

**顺序固定**

1. 导出相关表的真实DDL、索引、约束及权限；做一致数据库备份，记录表计数与验证hash。备份/含个人正文的迁移数据只放受控存储，不进公开源码仓库。
2. 在同一数据库只读快照中读取当前全文、实际cuts/summary、节点、事件、图片、题库/作答。已有分段计划的文章建立Git基线时严格沿用原切点，不重新分段。尚未精读、没有reading_articles计划的已保存文章，由平台承担一次首次主旨/分段生成后建立基线；失败记待迁移，不伪造空cuts把整篇永久固化成一段。有节点但缺计划属于异常，不能用新分段冒认旧锚点。历史上已被覆盖且无备份的原文不能凭空重建。
3. 每个基线段独立UUID，重复文字不同ID。当前真实全文、切点与节点锚点不一致时，形成阻断报告，不能按标题相似度拼接。
4. 迁移参与账号集合来自真实uid的阅读事件、节点生成者和作答记录。每位参与账号继承其文章上原本公开可见的init/explain骨架，以及本人的ask和后代；每用户独立复制，不创建跨uid父边。其他人的ask及其依附私有子树不能当作公共祖先复制。
5. 用“用户uid+旧node_id→新node_id”映射重建父链、supersedes及事件引用。旧节点uid只是生成者，不代表整树独占所有权。记录migrated_from_id；初始化来源版本并标记迁移来源，不生成任何收费流水。
6. 沿父链传播可见性：祖先含ask时，该分支仅ask所属账号可迁移；遇多个不同真实uid的私有祖先、缺父、环、anon/self或无法验证归属，保留原始备份并记录异常，不复制给任意账号。存在这类未处理阻断项时不得宣布迁移完成。
7. 旧cuts本来是Python码点，保持；旧JS选区和图片位置按实际对应父文本将UTF-16转码点。不能统一批量套一种转换；越界、代理对中间、父文本缺失均进入异常报告，保留原数字，禁止自动裁短再声称正确。
8. 基线题库和图片解释绑定基线commit，作答带对应quiz_hash；进度绑定基线段ID。重复初始解释或重叠旧范围需在报告中确认可保留的修订，不静默选第一条删除其余。
9. 验证每个新父子同uid/article/segment、范围合法、每段活跃init唯一、无节点丢失或误复制私人分支；核对旧到新映射计数、每账号可见内容样本。Git所有基线可还原，DB当前投影与Git一致。
10. 切换读写到新契约后清内存缓存，重新登录核对两账号隔离；只有验收通过才恢复写入。充值是否开放仍待 JM 最终确认，不随迁移自动开启。

回退：尚未开放真实计费时可在维护窗口恢复迁移前备份和旧应用，同时停用新写入；保留新Git候选用于核查。产生真实支付或积分流水后，禁止用旧DB备份覆盖现有账本；故障时关闭新生成/充值入口，保留账单与查单退款恢复服务，修复后前向恢复。不能以“回滚发布”撤销真实到账或丢弃已消费流水。

`core/ai.py` 的明确内部接口：prepare阶段返回 `{messages,requested_model,max_tokens,temperature,json_mode}`，只构造输入不发请求；execute阶段返回 `{content,response_id,returned_model,created,finish_reason,usage}`。现有平台功能用薄包装取得原str/dict返回值；收费入口交给billing编排。禁止用隐式全局当前用户/可变单例把不同请求的账务上下文混在一起。

### B.16 HTTP、响应样例及交付判定

错误响应固定为 `{ok:false,error:{code,message,details?}}`。message供人阅读；前端分支仅依赖code。非本人对象与不存在对象保持相同404，不在details透露他人标识。details里的微积分/金额及bigint同样按B.2编码。

| HTTP | code | 客户端处理 |
|---|---|---|
| 401 | LOGIN_REQUIRED / SESSION_EXPIRED / ACCOUNT_ID_REQUIRED | 保留当前阅读位置，走已有重新授权；不自动执行未获确认的付费意图 |
| 403 | ORIGIN_NOT_ALLOWED | 拒绝跨站写入；不刷新重试 |
| 404 | ARTICLE_NOT_FOUND / VERSION_NOT_FOUND / SEGMENT_NOT_FOUND / NODE_NOT_FOUND / OPERATION_NOT_FOUND / ORDER_NOT_FOUND / REFUND_NOT_FOUND | 停止请求；不能回退到他人节点或另一原文版本 |
| 402 | INSUFFICIENT_CREDITS | details返回所需Token、当前周期可用Token和钱包可用积分；保留已有内容。充值关闭时不展示可用入口 |
| 409 | IDEMPOTENCY_CONFLICT / VERSION_CONFLICT / SELECTION_OVERLAP / PARENT_CHANGED / REGENERATION_INTENT_MISMATCH / QUIZ_VERSION_MISMATCH | 展示具体冲突并刷新相关只读状态；不得静默改输入后重发 |
| 409 | OPERATION_IN_PROGRESS | 仅本人同意图时details返回原operation_id，轮询该操作，不新增冻结 |
| 410 | QUOTE_EXPIRED / BOOKMARKLET_UPDATE_REQUIRED / ARTICLE_UPDATE_REQUIRES_IMPORT | 新报价、升级书签或使用新导入入口；不兼容执行旧付费请求 |
| 422 | INVALID_INPUT / INVALID_OFFSET / QUOTE_REQUIRED / INVALID_REFUND_AMOUNT | 修改输入；缺报价不能直接生成 |
| 429 | RATE_LIMITED | 按Retry-After退避；重放原幂等键，不换键绕限流 |
| 503 | BILLING_CONFIG_UNAVAILABLE / RECHARGE_UNAVAILABLE / VERSION_STORAGE_UNAVAILABLE / DEPENDENCY_UNAVAILABLE | 相应新动作暂停；已有操作继续原ID查询和恢复 |

后台任务失败由GET操作接口HTTP 200返回其持久终态及error_code；不要把轮询中的waived_failure伪装成一次全新的HTTP生成失败并自动重提。Git更新冲突同理：GET任务返回state=conflict和latest_commit，最终提交前的同步基线冲突才直接HTTP 409。API不会因为给出了message就省略稳定code。

**报价样例（纯测试数据）**

输入上界300 Token、输出上限100 Token，因此报价上界为400 Token，即400积分。报价本身不冻结，execute成功预留后才按原周期额度优先、钱包补足的顺序冻结。有效期从示例时间起60秒；所有示例UUID和commit均为测试占位数据。

```json
{
  "ok": true,
  "operation_id": "00000000-0000-4000-8000-000000000001",
  "action": "init",
  "status": "quoted",
  "quoted_points": 400,
  "reserved_tokens": 0,
  "usage_tokens": 0,
  "daily_consumed_tokens": 0,
  "wallet_charged_points": 0,
  "expires_at": "2026-09-15T00:01:00Z",
  "result_node_id": null,
  "error_code": null,
  "billing_rule": "1 Token = 1 积分"
}
```

`reserved_tokens` 是该操作历史预留的总Token上界；quoted状态为0，execute完成预留后为400，终态仍保留供审计。当前冻结量必须从`daily_token_quotas.reserved_tokens`和`credit_wallets.ai_reserved_microcredits`读取，不能把历史预留字段当作当前冻结展示。

**必须固定的最后几项契约**

- 所有有副作用的POST使用已有业务幂等键或operation_id。跨进程不靠前端按钮禁用保证幂等；同键不同请求永远不覆盖原单。
- 请求指纹使用经校验/规范化后的字段白名单，键排序JSON，再SHA256；包含动作、文章、版本、段、父/替换ID、码点范围、精确问题以及相关订单档位/金额。缺省值先展开为明确null/固定默认；生成时间、执行者token不参与请求指纹。Git使用原文字节，不受此JSON规则改变。
- wallet、ledger和operation/order/refund的引用采用数据库外键；相应身份和金额创建后不可改。ledger.kind仅允许ai_reserve/ai_settle/ai_release/payment_credit/refund_reserve/refund_settle/refund_release，按kind核对三个业务引用恰好一个非NULL，并要求引用对象uid等于流水uid。
- 已成功充值单只以可信查单为paid；created也是可查询状态。已失败/关闭支付单不得由普通乱序数据恢复pending，遇可信SUCCESS必须核验并按唯一入账事务处理，不能因本地曾失败而漏掉真实收款。
- 正常关闭页面不取消已受理生成；首版不增加中途取消协议。明确重新生成属于新付费意图，必须重新报价。
- 已归档但未删除的节点可以通过本人历史修订入口读到；普通生成入口的目标必须属于有效当前分支。节点生成版本不强制等于当前所查看原文版本，段成员检查仍强制执行。
